# together-listen V2 技术决策记录

## 1. 项目目标

项目定位：轻量级多人同步听歌服务。

目标环境：

- 服务器：2H2G
- 单房间：2-3人
- 后续：多个小房间，总在线约10人级别

核心目标：

- 稳定运行
- 简单维护
- 低资源消耗
- 保留未来扩展能力

---

## 2. 为什么继续使用 Node.js

决定：保留 Node.js。

原因：

- 项目核心是实时通信，而非计算密集型任务
- Socket.IO 生态成熟
- 开发效率高
- 当前代码基础可以平滑迁移

暂不迁移 Go/Rust。

原因：

- 当前瓶颈不是性能
- 重写成本高
- 会引入新的维护成本

---

## 3. 为什么使用 TypeScript

决定：逐步迁移 TypeScript。

原因：

- 当前 server.js 职责较多
- 类型约束可以降低维护风险
- 方便模块化拆分

---

## 4. 为什么暂不使用微服务

决定：采用模块化单体。

原因：

- 用户规模较小
- 服务器资源有限
- 微服务增加部署复杂度

未来达到更大规模时再评估拆分。

---

## 5. 为什么优先 SQLite

决定：使用 SQLite 作为第一阶段持久化方案。

原因：

- 零额外服务
- 资源占用低
- 适合小规模应用
- 备份简单

未来如规模增长，再迁移 PostgreSQL。

---

## 6. Redis 使用计划

当前不引入 Redis。

原因：

- 当前规模无需分布式状态
- 单实例内存状态足够

未来需求：

- 多节点部署
- 房间状态共享
- WebSocket 集群

达到条件后再引入。

---

## 7. 框架选择

当前：Express + Socket.IO。

暂不强制迁移 NestJS。

原因：

优先解决业务模块边界，而不是更换框架。

---

## 8. 最终技术路线

V2：

Node.js
+ TypeScript
+ Express
+ Socket.IO
+ SQLite
+ PM2
+ Nginx
